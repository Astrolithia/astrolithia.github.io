消息队列有一个很重要的技能就是削峰填谷

对中间件而言 架构要精简 尽量避免依赖其他三方组件
RocketMQ 为了保证消息队列写消息的性能，会将所有的 topic 都写入到同一个文件里，也就是：顺序写，在很多地方都有应用，比如 MySQL 的 redolog
如何保证消息一定发送成功：Broker 接受成功后，返回 ack 给生产者，没接收到 ack 则不认为消息发送成功，进行重试

发送异步消息需要提供一个方法，方法里面定义了 onSuccess、onException，会有另外的线程来处理 Broker 的响应，如果接受到成功的响应就会执行 onSuccess 的逻辑，如果发送失败，会执行 onException 的逻辑，可以在这个逻辑里面实现失败的记录数据
它跟同步消息的区别主要在于场景的应用，同步消息需要等待前一条消息的响应才能继续法后面的消息，异步消息不需要等待，适用于对响应时间敏感的场景
不论是同步消息还是异步消息，都会关注发送完消息 Broker 的响应，但是有些场景压根就不关心这个结果，即生产者只管发送消息，至于 Broker 有没有收到消息，生产者不关心，不需要等待响应
比如日志的收集，日志的量级很大，但可靠性的要求不高，因此非常适合使用单向消息
顺序消息：按顺序发布消息，并且按发布消息的顺序来消费消息
一个很常见的例子就是订单场景：

  1. 创建订单
  2. 支付
  3. 发货
  4. 完结订单

    但是每个消费者消费的速度是不一样的，我们保证不了他们的消费速度
    可能消费者-2 消费了支付的消息，而消费者-1 还没消费完创建订单的消息，这样业务顺序就乱了
    如何解决这个问题：把这几个消息都发送到一个队列，那就是顺序消息
    如果把创建订单、支付、发货、完结订单，这几类消息全都发往一个队列，这叫全局顺序消息

    如果把同一笔订单的创建、支付、发货、完结发往一个队列，不同的订单可以发往不同队列，这叫分区顺序消息

    理论上分区顺序消息够用了，而且分区顺序消息的并发度更好，从上图来看，消费者 1、2 能同处理订单-1 和订单-2 ，如果是全局顺序消息，那么只有消费者-1 一个人在干活
    假设要实现全局顺序消息，那么生产者将这几个消息都指定往队列 1 发送，即可实现全局顺序消息
    如果是分区顺序消息，生产者只依靠一个叫 sharding key 的东西来区分即可，比如订单的场景可以将订单号作为 sharding key，在发送消息的时候，根据 sharding key 来选择队列即可
    延迟消息：生产者发送了消息，但是并不想立马被消费者消费，希望延迟一段时间后才能被消费，比如订单取消场景，一般我们下单后，如果 15 分钟没有支付，这笔订单就需要被取消，这个场景我们就可以在下单时候同时发送一个订单取消的延迟消息，时间是 15 分钟，这样 15 分钟后消费者就能收到这个消息，然后看看此时的订单有没有被支付，没支付就执行订单取消
    RocketMQ 实现延迟消费的方法：
    延迟消息一开始不放在正常的 Topic 中，RocketMQ 专门搞了一个 Topic 叫 SHEDULE_TOPIC_XXX，将所有延迟消息都放在这个 Topic 下，然后有定时任务来扫描遍历消息的延迟时间到了没，如果到了，那么再把延迟消息发往它本身对应的 Topic 队列中
    这样就保证了延迟消息到时间以前，消费者不会消费到这个消息，然后一到时间，消息就被投递到原来的 Topic 上，这样消费者就能消费到了

    批量消息：一次性打包发送多条消息，在对吞吐量敏感的场景，批量消息就非常合适
    正常的消息是一条一条发，然后一条一条的等待响应，而批量消息是一批一批发，比如 100 条消息，本来需要调用 100 次发送接口，且需要等待 100 次响应，现在将这 100 条消息打包成 1 条消息发送，仅需调用 1 次发送接口，且等待 1 次响应

批处理思想很关键，像 Kafka 底层默认会帮我们批量打爆发送消息，所以 Kafka 的吞吐量更大

NameSrv：这个看板对应到 RocketMQ 中的角色名叫 NameSrv，即命名服务
待 Broker 启动后，Broker 将自己的一些信息上报到 NameSrv 上，并且每过 30s 也会上报自身信息至 NameSrv
NameSrv 每 10s 会扫描它记录的 Broker 记录，看看这些 Broker 是否还活着
具体判断存活的方式是看 120s 内该 Broker 是否有上报自身消息至 NameSrv，如果超过 120s 都没有，那么 NameSrv 会移除这个 Broker 相关的信息，表示该 Broker 下线了
NameSrv 与 Producer：对于 Producer 来说，启动后它需要找到一台 NameSrv 进行关联，即进行长连接的建立，因为 Producer 需要知晓它将要发送的 Topic 应该发往哪个 Broker，具体的 Broker 地址又是哪，所以 Producer 需要从 NameSrv 或者有关 Topic 的路由信息，然后跟对应的 Broker 建立长连接，后面直接将消息发送给对应的 Topic，并且 Producer 每过 30s 会从 NameSrv 获取 topic 和 broker 最新的映射关系到本地，如果发现有新的 Broker 出现，那么就会跟新的 Broker 简历长连接，Producer 不会缓存路由信息到本地文件中，只会放在内存里，如果 NameSrv 挂了，由于 Producer 是直接跟 Broker 简历长连接直接发送消息的，所以不影响现有的消息发送，但是如果这时候将 Producer 重启了，那么在 NameSrv 挂了的情况下，消息就无法正常发送了，因为路由信息都丢了，也无法从 NameSrv 获取。如果在线上遇到类似这种情况，切忌不要随机重启 Producer，要先定位问题，盲目重启可能产生更大的资损

如果 NameSrv 挂了怎么办：新接入的 Producer 和 Consumer 就成为瞎子了，一个不知道将消息发往哪，一个不知道从哪里获取消息，业务就会受到阻碍。为了避免单点故障，在生产环境一般部署多台 NameSrv 形成 NameSrv 集群，这样一来假设发生了意外，一个 NameSrv 挂了，那么别的 NameSrv 可以顶上。
RocketMQ 实现的 NameSrv 非常轻量级，集群内的 NameSrv 是互相独立的存在，它们之间不会进行任何的信息交互

消息存储在 Broker，那么到底是消费者去 Broker 讨要消息，还是 Broker 将消息送到消费者手上
消息的消费或者说可以接收其实跟收快递是一个道理
快递的接收现在一般有两种模式：

  1. 快递员送货上门
  2. 我们去驿站（丰巢柜）拿快递
    快递员送货上门对应 Broker 将消息推送给消费者
    我们去驿站（丰巢柜）拿快递对应消费者主动去 Broker 拉消息

推消息：指的是 Broker 收到对应的消息，立马将消息推送给消费者，这种方式的优点是：消息的实时性非常高，并且对消费者而言实现比较简单，啥都不用干直接等着消息上门即可
缺点也明显：消费者在某个时段可能非常忙，没有时间来处理新的消息，而 Broker 还在一直把消息推过来，可能会直接把消费者干爆了
在推送消息给消费者之前，先打探下消费者的情况，就好比快递师傅会一个一个打电话确认是否在家
推模式适用在消费者不多、消息量不大、及时性要求高的场景
拉消息：消费者主动去 Broker 拉取对应的消息
主动权掌握在消费者手上，每个消费者可以根据自身当时的情况，选择合适的时机去 Broker 拉取消费
在推消息的场景，Broker 可以来一条就推一条给消费者，也可以缓存一定数量的消息再推，但是就像我们说的，每个消费者的情况不一样，所以推模式具体缓存多少数量消息再推很难有个定数
缺点也很明显：消息的消费可能不及时，假设定时 1 分钟去拉一次，发现没任何消息，而恰巧嘴一条消息刚好在消费者拉取请求后存储到 Broker。如果定时拉取的时间改短一些，消费不及时的现象可以得到缓解，但是同时也带来了另一个问题：消息忙请求。忙请求很好理解：假如我们设置每 1s 去拉取消息，那么即使当前几个小时内都没消息投递过来，我们也需要持续性去请求 Broker，尝试去拉取消息

ActiveMQ 用的就是推模式，而 RockerMQ 和 Kafka 用的就是拉模式
ActiveMQ 上个时代的产物，而 RockerMQ 和 Kafka 如日中天
它们没有使用朴素的拉模式，而是采取了一种变种拉模式：长轮询
消费者发送拉取请求到 Broker 时，如果此时有消息，Broker 直接响应回消息，如果没消息就 hold 住这个请求，比如等 15s，如果 15 秒内有消息过来就马上响应这个请求返回消息，如果没有消息则返回无消息
RocketMQ 的 pushConsumer 实际上是伪推模式，底层的实现还是基于长链接的长轮询去拉取消息

DefaultMQPullConsumer 跟 DefaultLitePullConsumer 有什么区别：前者需要自己获取队列，对每个队列调 pull 并传入 offset，还要自己管理和持久化位点、做负载均衡、写拉取循环和流控。DefaultLitePullConsumer 是 4.6.0 起官方推荐的替代品，API 风格接近 Kafka Consumer：后台线程自动预拉消息到本地缓存，你只要调用 poll 取消息。支持 subscribe 自动负载均衡和 assign 手动指定队列两种模式，位点默认自动提交，也能改成手动 commit，另外还内置了 seek、pause/resume 和流控
DefaultMQPullConsumer 什么都要自己管，比如拉取哪个队列、从哪拉、拉完记到哪里

消费者启动：首先去找看板（NameSrv），启动时需要指定 NameSrv 的地址，紧接着它根据自己的订阅，连上了 Broker 后，Broker 也知晓了这个消费者的存在。紧接着就要做一件很重要的事情：分赃，而且是合理的分赃
消费者实际是去 Topic 下的某个队列获取消息，假设 Topic 有 4 个队列，此时消费组 A 只有一个消费者，那么毋庸置疑，这个消费者需要消费这 4 个队列的消息。那么假设消费组 A 新来了一个消费者，那么此时就需要将这个 4 个队列分 2 个给新来的消费者，这样减轻了老消费者的压力，也提供了消费的效率，这就是所谓的分赃
分赃的具体过程也简单：由消费者遵循一定的规则主动来分的
消费者收到要分赃的通知后，获取这个 Topic 下的所有队列，比如队列-1、队列-2、队列-3、队列-4，紧接着获取订阅这个 Topic 的消费组下的消费者信息，比如消费者-1、消费者-2
这个分赃的专业名字叫：重平衡，也是客户端的负载均衡
如果这个消费组的消费者数量比 Topic 的队伍数量少，此时增加消费者可以缓解消息堆积。如果消费者数量比队列数还多，则没用
不仅仅是消费者启动的时候会触发重平衡，每个消费者也会有个定时任务，每 20s 主动重平衡下，也就是负载均衡了，防止消费任务不均衡
并且，如果有消费者下线了，由于消费者和 Broker 建立了连接，下线后 Broker 可以知晓这个情况，此时 Broker 也会通知所有消费者进行重平衡

重平衡后，每个消费者都知晓它所负责的是哪个 Topic 下的队列，下面的任务只要去 Broker 拉取对应队伍的消息就行了。具体如何拉：最简单的想法肯定是一个队列对应一个线程，然后由每个线程负责去拉取对应的消息，但是队列可能很多，与之对应的线程也会很多，线程多了并不是好事，因为上下文切换频繁会带来损耗
由于重平衡的机制，对应的队伍数量也是变化的，队伍变化后，对应的线程也要变，那不还得管理线程的生命周期
RockerMQ 只用了一个线程（叫 PullMessageService）来执行拉消息的操作，所有的拉取消息的动作都会封装为 pullRequest，扔到 pullRequestQueue 这个阻塞队伍里面

消息点位
广播模式下，消费点位将存储在消费者本地磁盘上，因为广播模式是将消息广播给每个消费者，它不需要有统一的地方来管理这个位置，每个消费者自己维护就行
集群模式下，就不能本地维护了

VCS（版本控制系统），比较流行的 VCS：git
如果想在 git 执行提交操作前运行什么命令，就需要创建一个 .git/hooks/pre-commit 文件，来告诉 git 我们要在提交阶段做一些事情
.git 目录作为 git 在本地管理状态的文件目录，一般是不会提交到远程仓库的，因此在这个目录下做的任何改动，都是无法共享给其他协作者的。那么在这个情况下，就非常需要一个工具帮我们把想要同步给其他协作者的的配置同步到他们的 .git 目录下
一般我们会使用 husky 这个工具，使用方式是通过包管理工具 npm 或者其他包管理工具安装
